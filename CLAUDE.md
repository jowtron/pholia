## CORS / Auth — Critical Knowledge

This is the single most important section. These learnings were hard-won through extensive debugging.

### The CORS saga

1. **ABS CORS setup:** `ALLOW_CORS=1` env var on the ABS Docker container.

2. **ABS OIDC update broke CORS:** An ABS update added OIDC support, which adds `access-control-allow-credentials: true` to all responses. Combined with `access-control-allow-headers: *`, this violates the CORS spec (wildcards are invalid when credentials are indicated). Safari enforces strictly and blocks all requests.

3. **Fix — use `?token=` query parameter auth** instead of the Authorization header. ABS supports `?token=<jwt>` on all API endpoints. GET requests need no CORS preflight; POST only needs `Content-Type` allowed. Faster too.

4. **All fetch calls must use `credentials: 'omit'`** to prevent Safari's tracking prevention from blocking responses with `Set-Cookie`.

5. **ABS caches CORS origin incorrectly:** ABS reflects only one origin at a time. If a different client (Go proxy, ABS web UI) makes a request, ABS may start reflecting that origin instead of `pholia.pages.dev`. Fix: restart ABS Docker container. Avoid mixing clients.

6. **`Content-Range` is NOT CORS-safelisted.** ABS doesn't add `Access-Control-Expose-Headers: Content-Range`, so JS can't read it from a Range response. Use HEAD's `Content-Length` for size discovery — that header IS safelisted.

### Connection-failure recovery

When a fetch fails for any reason (server down, network blip, sleeping
laptop hosting ABS), Pholia surfaces a tappable link to the ABS URL so
the user can poke the server in their browser, plus auto-retries on
`visibilitychange` and `online` events.

- Login failure shows a tappable link to open the ABS URL directly
- Saved-session failure shows "Open server to test connection" + Retry
- Auto-retry on `visibilitychange` and `online` events

## Service Worker — Critical Architecture

These behaviors are *load-bearing*; understand them before editing `sw.js`.

### Selective interception — all-worker or all-native per file

**iOS's media loader cancels a resource whose CORS status changes between Range responses.** A response the SW synthesizes (it carries `Access-Control-Allow-Origin: *`) and a native no-cors media request have different statuses, so for one media load the SW must answer *every* request for that file or *none* of them. Mixing was the real reason "partial cache breaks iOS" (2026-09-03: cached header, then the file tail re-requested natively every 170 ms until the loader gave up).

So the page announces each media load: `App.pinMediaMode(url)` posts `MEDIA_LOAD` over a MessageChannel before `audio.src` is assigned (`Player.loadTime`, `onTrackEnded`), and the SW pins a mode per file (`modeFor`): `sw` when the file is fully cached, or partially cached with the Settings toggle "Play from partial cache" on (default on); otherwise `native`. In `sw` mode `serveChunked` streams the contiguous cached run and bridges everything else from the server inside the same 206 via `corsFetch` — a CORS `fetch` carrying **only** `Range` (the media element's own headers include iOS's non-safelisted `X-Playback-Session-Id`, which forces a preflight). The bridge starts when the response starts, so the server's cold first byte overlaps cached playback. In `native` mode the fetch handler returns without `respondWith`. Pins and both flags persist in the `pholia-sw-config-v1` cache because iOS restarts the worker constantly; a fresh worker awaits its key map for audio requests rather than passing the first ones through. Un-pinned files fall back to the old rule (fully cached → SW, else native).

The original reason for not intercepting everything still stands: iOS WebKit adds latency to every SW-intercepted media fetch, so uncached files stay native (regression 85caf8b, fixed 1bb9705).

The SW maintains an in-memory `cachedKeys` Set / `cachedMetas` / `cachedChunks`, populated from `cache.keys()` at activate, on `MEDIA_LOAD`, and when the page sends `CACHE_CHANGED` after chunk writes/deletes.

### Chunked offline audio cache

Audio files are cached in **10 MB chunks** (NOT as whole-file Responses). One `cache.put` of a multi-hundred-MB Response OOMs iOS PWA (~50 MB working budget per tab). Chunked downloading keeps memory peak at ~10 MB regardless of file size.

Per track: N chunk entries plus one meta entry (`totalSize`, `chunkSize`, `numChunks`, `contentType`, `sticky`).

**Meta is written *up front* before the chunk loop**, not at the end. With sliding-window auto-cache the loop sleeps indefinitely waiting for playback to catch up to ahead-of-window chunks, so a trailing meta-write would leave coverage queries returning null for most of a session. As a consequence:
- "Meta exists" no longer implies "fully cached" — `isDownloaded`, `fullyDownloadedIds`, `bookSize`, and `cleanupPhantoms` all walk actual chunk presence (don't trust meta alone).
- `cleanupPhantoms` preserves any entry with at least one cached chunk; only fully-orphaned meta is dropped.

**Cache keys MUST use query params, NOT URL fragments.** The Cache API spec strips fragments before storing or matching, so `url#chunk=0`, `url#chunk=1`, `url#meta` all collapse to the same key — every write overwrites the previous one. Use `url?__chunk=0`, `url?__meta=1` instead. (This bug caused weeks of mysterious "downloads complete instantly", "1 byte cached", "all chapters falsely green" symptoms.)

The SW reassembles chunks on the fly when the audio element makes Range requests; for a worker-pinned file, bytes it doesn't have are bridged from the server in the same response (see above) — never by letting the request go native.

### Cache versions

**A no-cors `<img>` response is opaque: `status` is 0 and `ok` is false whether the server said 200 or 404.** `handleCover` cached opaque responses (it has to, or the cover cache never fills from normal UI loads), so a cover that 404'd once — every mp3 book with no embedded art — stayed a broken image on that device forever, even after the server learned to serve one. It now asks with `mode: 'cors'` first, which the shim allows on covers, and caches only a real 200; a genuine 404 is returned uncached so the next view asks again. `COVERS_CACHE` went to v2 to drop the entries poisoned by the old rule.

- `pholia-v5` — app shell
- `pholia-offline-audio-v2` — chunked audio + covers (v1 used the broken fragment keys; v2 is auto-cleaned by activate)
- `pholia-offline-meta-v1` — per-book metadata JSON

`KEEP_CACHES` filters which survive activate cleanup. Bump the audio cache version when changing the chunk format.

## Offline mode — Two flavors

### Explicit Download (sticky)
- "Download for offline" button on book detail
- Fetches every track end-to-end in chunks
- Writes meta with `sticky: true`
- Survives auto-cache eviction
- Shows in Settings → Downloaded

### Cache while playing (sliding window)
- Settings toggle, **default off**
- Active during playback (5 s after `startItem`)
- `saveMeta` runs at the *start* of `_startAutoCache` so the book persists across PWA restarts and shows in Settings → Cached even if the loop never finishes
- Chunk-level filter: only caches chunks whose playback time is between `(playhead - 30 min)` and `(playhead + 1 hr)`
- `shouldCache` filter skips behind-cutoff chunks; `beforeChunk` sleeps for ahead-of-window chunks
- After each chunk caches, evicts chunks of the current track more than 30 min behind playhead — but only on `sticky: false` entries
- Cache footprint stays bounded (~1.5 hr of audio at any time)
- Sticky preservation: meta writes never downgrade a previously-sticky entry

### Chapter cache UI

The green overlay on chapter rows reflects *actual* chunk coverage, not `received/total` ratio. Computing fill from `received/total` was wrong for sliding-window because `received` only sums the in-window chunks (~5% of file), so the fill drew from byte 0 to 5% of the book — making it look like only the start was cached.

`Offline.chunkCoverage(item)` does one `cache.keys()` walk and returns per-track `{ totalSize, chunkSize, numChunks, cached: Set<int> }`. `_chapterCovered` maps each chapter's playback-time range to a byte range, then to chunk indices, and only marks the chapter green when *all* overlapping chunks are present. The fullscreen player chapter list and the detail-page chapter list are both painted by the same code path.

## SW Update Flow

- `_headers` has explicit per-file rules. **Do NOT add wildcard rules** — Cloudflare Pages headers are *additive*, so multiple matching rules concatenate. A wildcard `Cache-Control` plus the `/sw.js` `no-cache` resulted in `max-age=86400, ..., no-cache, ..., max-age=86400` — Safari picked one of the long values and cached `sw.js` for 24 hours, breaking all updates. Fixed in f79d8b3.
- `App._pollForUpdate()` awaits `reg.update()`, then awaits the installing SW's `statechange`, then polls `reg.waiting` for up to 10 s (re-fetching the registration each iteration — iOS PWA can be slow to reflect state).
- **`App._checkBuildVersion()`** runs in parallel: fetches `/index.html` with cache-bust, parses the deployed git hash from `#build-version`, and shows the update banner on mismatch. This is the load-bearing path on iOS PWA — `reg.update()` doesn't always re-fetch `sw.js` byte-for-byte even with no-cache headers, so the SW poll silently misses updates and only the version probe catches them. Without it, the only reliable update triggers are the manual "Check for updates" button and force-quitting the PWA.
- Polled from: initial setup, `visibilitychange`, every `switchTab`/`pushNav` (debounced to 10 s).
- Banner has 12 s reload failsafe. The banner click handler falls through to `window.location.reload()` when there's no `reg.waiting` (covers the version-probe path where SW hasn't picked up the new sw.js yet). The manual "Check for updates" button runs both probes and shows "Up to date" when neither finds anything — it does NOT auto-reload (a previous brute-force reload here caused user confusion).

## Persistent Login (PWA)

- Credentials in localStorage: `pholia_server`, `pholia_username`, `pholia_token` (one-time migration from `cadence_*` runs at the top of `api.js`)
- `tryAutoLogin()` restores session on page load
- Only clears token on 401/403 — network errors preserve token + show retry UI
- **An iOS home-screen app is a separate storage partition.** Nothing saved while running in Safari (localStorage, cookies, Cache Storage) exists in the installed app; only passkeys (iCloud Keychain) and the manifest's `start_url` cross over. Two things lean on that (2026-09-05):
  - `functions/manifest.json.js` serves the manifest with `start_url=/?server=<url>&u=<username>` taken from the `<link rel="manifest">` query (`?s=&u=`) or the `pholia_install` cookie. **The link is written by an inline `<head>` script** (from the `#connect=` fragment or the saved `pholia_server`) with `crossorigin="use-credentials"`: iOS resolves the manifest from the link as parsed and sends no cookies without that attribute, so the first version (a static link rewritten later by `ABS.setInstallHint`) installed an app with an empty login form. `setInstallHint` still updates the href/cookie for a server switch later in the same page load. `App._consumeInstallHint()` (first thing in `tryAutoLogin`) adopts it as the login-form prefill when the partition has no `pholia_server`, then strips it from the URL. `sw.js` strips `server`/`u` from the shell cache key so an offline launch still hits the precached `./`. The manifest has `"id": "/"` so the changing manifest URL is still one app. **The token is never put in `start_url`** — it would live in a launch URL forever.
  - **Token-only vault entries** (`abs_servers.encrypted_token`, schema 0003; `POST /api/servers` takes `password` and/or `token`, `GET /api/servers/:id` returns both, null when absent). The ABS_shim hand-off (`_consumePholiaHandoff`, `#connect=` fragment from the shim's "Open Pholia") signs in with a token and no password ever passes through Pholia, so after it lands `_maybeOfferSaveToAccount({token, handoff:true})` rewords the save-to-account modal ("Sign in with Face ID next time?") and the vault entry holds the token. `loginFromAccount` uses the password when there is one, else `ABS.authorize()` (`POST /api/authorize?token=`) and re-saves the fresh token. Because the local copy and the vault copy would otherwise expire on the same day, `_maybeRotateToken` runs on every ordinary auto-login once the JWT `exp` is within 20 days and pushes the new token into the vault — but only into an entry that already exists (a declined "save to account" stays declined). A user who doesn't open the app for a whole token lifetime (30 days on the shim) is asked for their password, with server + username prefilled. Settings → "Save current server to account" still asks for a password on purpose: real ABS ≥2.26 access tokens are short-lived, so a token entry is only ever created from the shim hand-off.
- **Signing in with an email (ABS_shim, 2026-10-14).** The shim's `/login` also takes the account's email in the username field (stock ABS doesn't, so the field still says "Username"). `handleLogin` therefore saves the server's own `data.user.username`, not what was typed, in `saveCredentials` and the save-to-account offer: the vault is unique per (server, username), and the persisted tabs, the known-offline list and the install hint are all keyed by the username, so an email would have split each into a second copy. Vault logins replay the saved name and are unchanged.
- **"Forgot password?" (ABS_shim only, 2026-10-14).** Under the login form, shown when the server in the form answers its public `/status` with the shim extra `passwordReset` (a path, `/reset`); stock ABS has none, so nothing shows. `ABS.passwordResetPath()` asks once per server per page load (an unreachable server is asked again), `App._offerPasswordReset()` runs after a failed sign-in, on the vault-login error path (`_showLoginScreenWithError`), when a saved token gets a 401 at launch or on retry, and when the server or username field changes. The link opens the shim's own page in the browser with `?u=<username>`. A reset on the shim signs every device out (a token cut-off), so the saved token here gets a 401 and the prefilled form takes the new password; with a Pholia account signed in, `_maybeOfferSaveToAccount` then updates the Face ID vault entry silently. `ABS.login` errors now carry `status`. Shim side: ABS_shim CLAUDE.md "Passwords".

## New-episode notifications (ABS_shim push, 2026-10-13)

Tap the bell on a show's page and the phone gets a notification when that show has a new episode; tapping it opens the episode's page. Ported from TinnyGo's proven Web Push (`~/Claude_Code/Islandpool/docs/web-push-export.md`), with its known weaknesses fixed. NOT YET SEEN on a phone.

- **The shim is the sender.** It polls the feeds, so it knows when an episode lands, and it holds the VAPID keys, the subscriptions and each user's per-show choice: `GET /api/push/status` (`{configured, publicKey, shows, subscriptions}`), `POST /api/push/subscriptions` (upsert by endpoint), `POST /api/push/unsubscribe`, `DELETE /api/push/subscriptions/:id`, `PUT /api/push/shows/:id {notify}`, `POST /api/push/test` (the real per-device outcome). It sends one notification per show per feed check that stored genuinely new on-show episodes, payload `{title, body, tag: 'show-<id>', libraryItemId, episodeId, kind: 'episode'|'test'}`. See the shim's CLAUDE.md. On stock ABS, or a shim that says `configured: false` (no VAPID secrets) or 404s, none of this shows.
- **Every push shows a notification** (`sw.js` `push`): parsed in try/catch, title falls back to 'Pholia', and a platform that refuses the options gets a plain one. iOS revokes the subscription of a site whose push shows nothing, so never add a "don't notify while…" check in the worker; anything that should not notify must not be sent.
- **iOS offers push only to an app added to the Home Screen and opened from there** (16.4+). A Safari tab has no `PushManager`, so the bell's tap says "Add Pholia to your Home Screen, then open it from there, to get notifications" instead of failing. Permission is asked inside the bell's tap with nothing awaited first (iOS needs the gesture). A denied permission can't be asked again from a page: the bell then explains Settings → Notifications → Pholia, and with the show off it shows only that text, no button.
- **The bell** (`_mountPushBell`, `_toggleShowPush`, in the show page's header, beside Follow / Following since 2026-10-14, and not drawn for a show the caller doesn't follow (`following: false`), since the shim sends pushes only to followers): off → permission → subscribe (`userVisibleOnly`, the shim's `publicKey`) → `POST /subscriptions` → `PUT /shows/:id {notify:true}`, in that order. On → `PUT {notify:false}` and the subscription stays (other shows). Status is cached five minutes (`_loadPushStatus`).
- **`ensurePushSubscription()`** runs once per page load per server and user (`_pushStart`, from `checkAbbSupport` once a shim is found) and 2 s after `controllerchange`, only when permission is already granted. It **always re-POSTs** the subscription, changed or not: the shim deletes a row whose push service answered 404/410, and this is what puts it back (and moves a phone to whoever is signed in now). **Key mismatch:** a subscription is bound to the key it was made with and Apple answers 403 to any other, so when `sub.options.applicationServerKey` differs from the shim's `publicKey` it unsubscribes, tells the shim to drop the old endpoint, and subscribes again. TinnyGo never did this, so its phones went deaf for good after a key change. A browser that doesn't expose the key is left alone.
- **How a tap routes.** `notificationclick` posts `{type:'open-episode', libraryItemId, episodeId}` to an open Pholia window and focuses it (never `client.navigate()`, which raced the focus in TinnyGo); with no window it opens `./#open-episode=<show>/<episode>`. Both are caught by the inline `<script id="push-tap-capture">` in `<head>`, before app.js loads, into `window.__pholiaOpenEpisode` (the hash is then stripped, like `#connect=`), because a tap that wakes a suspended app can deliver the message mid-boot. `_maybeOpenPendingEpisode` opens it once signed in: `showMain` defers it a task because every caller runs `switchTab('home')` straight after, which empties the nav stack. The episode page is a nav level, so Back returns to where the app was; a tap while an audiobook library is showing switches to the show's podcast library first. A 401 or offline (with no copy on the phone) keeps the target for the next sign-in.
- **Settings → Notifications** (`_renderPushSettings`): permission state, "Send test notification" with the shim's real answer device by device, the device list (service, added, "Last accepted" or "Never pushed to", a refusal newer than the last success, Remove), and the shows that are on (tap opens the show, Turn off). This device is the row whose id the last `POST /subscriptions` returned (`pholia_push_sub:<server>|<user>`); it has no Remove, because it would register itself again at the next launch.
- **Testing**: jsdom with `_shimCall` mocked to the contract, plus the worker's listeners against a fake `self` (bell order, mismatch re-subscribe, malformed payloads, both tap routes). Never trigger a real permission prompt from automation; the device test is Joseph's.

## Back goes back ONE level, and the stack knows how to redraw (2026-09-21, 04452ad)

`navStack` entries are `{title, render}`, not strings. `goBack()` pops, then calls the new top's `render()` with `_navRestoring` set; `pushNav` sees that flag and updates the level in place instead of pushing a second one, so a view needs no "am I being restored" branch — but **it must call `pushNav` before its first `await`**, or the flag is already cleared by the time it runs (that is why `showCollectionDetail` pushes a placeholder title and retitles after the fetch). `setNavTop(title, render)` retitles the current level and can swap in a cheaper redraw: `showBookDetail` hands over the item it already holds, so coming back to a book from an author or series page costs no round trip. Only when the stack empties does `goBack` fall through to `switchTab`. Until this landed the stack held titles alone and `goBack` always ran `switchTab`, so Home → book → author → back went to **Home**.

**The swipe-back animation direction is not symmetric.** On commit the outgoing page slides to `+width`, then the incoming one is jumped to `-width` with the transition OFF, rendered, reflowed (`void content.offsetWidth`) and animated to 0 — it comes in from the left, where it was sitting behind the page you pushed. Clearing the transform instead (the bug until 2026-09-21) leaves the armed `settling` transition to run the new page in from the *right*, chasing the finger. A `touchstart` also clears a stale transform first: a tab backgrounded mid-swipe throttles the settle timers to minutes and the page would otherwise stay parked off-screen.

Testing trap: both `updateUI` and this gesture are unobservable in a backgrounded browser-automation tab. `requestAnimationFrame` never fires there and `setTimeout` is throttled to roughly a minute after five minutes hidden, so a swipe freezes mid-flight and the JS tool times out. Drive `goBack()` directly to check the stack, and read the transform with `setTimeout` sampling rather than rAF.

A highlight built on either one is wrong half the time. Control Center and the lock screen already show the route. Availability and picker taps go to the audio debug log as `airplay-*` lines. The sleep and AirPlay buttons share `.fs-extras` at the sleep button's old 44 px height, which keeps the Chapters button, and the chapters page's bottom back button, where they were.


`#fs-chapter-list` used to live inside `.fs-bottom` capped at 250px, so tapping Chapters filled the bottom third with about five rows. It now sits in `#fs-chapters-panel`, a sibling of `.fs-bottom` positioned `inset: 0` and slid in from the right by `.fs-player.chapters-open`. `App.showFsChapters(bool)` drives it and is the only thing that should toggle either class — **it must keep the `hidden` class on the list itself in sync**, because `Player`'s tick reads `#fs-chapter-list.hidden` to decide whether repainting the rows is worth it. `closeFullscreen` resets to the player page.

**Swipe right with the chapter page already shut and the whole player drags away**, closing back to whatever opened it (`kind = 'dismiss'` in `_wireFsSwipe`). Tapping something in Continue listening lands you in the player, and the × is a long reach on a phone. It needs both speed and distance — a flick has to have covered `max(60px, 12% of the width)` — so a brisk swipe while reaching for the scrubber doesn't throw the player away.

The way back sits at **both ends**: `#fs-chapters-back` in the header and `#fs-chapters-back-foot` at the bottom, where the Chapters button that opened the page was — the same thumb that opened it closes it. The list needs `min-height: 0` or it refuses to shrink below its content and pushes that footer off the screen.

**One finger works everywhere in the player except `#fs-seek`.** It was limited to the artwork and the chapters header, which meant one finger got you TO the chapter list but two were needed to come back, because the rows filled the screen. A drag that crosses a chapter row sets `_fsDragged`, and the row's click handler ignores exactly one click after it, so a swipe doesn't seek.

`_wireFsSwipe()` makes it **drag with the finger**, not just react to a completed swipe: the panel tracks the touch 1:1 through an inline `transform`, and on release settles open past 30% of the width or on a flick (>0.8 px/ms and >40px). Two fingers work anywhere in the player; one finger anywhere except `#fs-seek`, where a horizontal drag is a seek (see the paragraph above — the artwork-only rule it used to have is gone). The gesture only engages after 12px of clearly horizontal movement, so vertical scrolling still works; `.dragging` on the panel turns the transition off and forces visibility mid-drag, and both it and the inline transform are cleared on release so the CSS class animates the last stretch. `_prepareFsChapters()` fills the rows when the drag engages, so a page sliding in is never blank.

Testing gestures in a background tab: **fabricate `event.timeStamp`** rather than sleeping between synthetic touches. Chrome throttles a background tab's timers to about one a second, so a realistic 16ms-per-move drag never completes.

## Content gestures: back, and pull to search (2026-09-06)

`_wireContentGestures()` puts two finger-following drags on `#content`, and one touch picks between them once, at 12px of movement:

- **Drag right anywhere on the page → back.** Armed whenever `navStack` is non-empty. That threshold used to be 2, so a book opened from Home had an empty-looking header, no back button, and neither the button nor the swipe did anything — the only way out was tapping a bottom tab. `goBack()` pops and redraws the level beneath — see the nav-stack section above; it only falls through to `switchTab` once the stack is empty.
  Commits past 30% of the width or on a flick; the outgoing page slides right, then the previous one is jumped to `-width` and animated in from the left (**not** by clearing the transform, which sends it in from the right). Only armed when the header's back button is showing (or on the Add screen, which `goBack` handles specially), so a tab's own home screen ignores it. It was edge-only at first, which was both hard to hit and, in a browser tab, impossible — iOS claims that edge for its own back gesture.
- **Drag down while `#content.scrollTop <= 0` → the inline search bar.** `#inline-search` sits in the flex column between the header and `#content`, height 0 until the drag grows it (damped, capped at 56px), so it pushes the list down instead of covering anything; dragging up puts it away. Typing runs `doSearch(q, contentEl)` — results replace the list, and Cancel or clearing restores it via `switchTab`. The header magnifier still opens the full-screen overlay; that path is untouched.

A drag starting inside a `.h-scroll` shelf is left alone **only while that shelf can still scroll right** (`scrollLeft > 0`); one already at its left end can't use a rightward drag, so the back gesture may have it. Anything not matching either shape releases the touch back to normal scrolling.

(The old edge-only version couldn't work in a browser tab at all, since iOS keeps that edge for its own back gesture. Starting the drag away from the edge avoids the conflict.)

## Player Quirks Learned

- **Don't add a buffering "recovery" that nudges `currentTime` after a stall** — it forcibly seeks during normal short buffer underruns and causes louder glitches than the brief stall would have. (Removed in 49924c9.)
- **No spinner on the play button.** Real audio players don't show constant buffering UI; users interpret it as "broken." Removed in f2e6c1c.
- **`preload='auto'`** on the Audio element so the browser buffers ahead aggressively. Helps but doesn't fix slow-network glitches by itself.
- **Pre-warm of next track** in multi-file books: when within 30 s of current track end, fetch first 256 KB of next track in background. Smooths the boundary swap.
- **Books without chapters must still scrub.** The mini and FS scrubbers represent *chapter* progress, not book progress. When `chapters` is empty (some ABS items have none), `getChapterProgress` and `seekToChapterPercent` fall back to whole-book progress/seeking — don't reintroduce a `if (!ch) return` early-out without a fallback or the scrubber goes dead.

## Common Pitfalls

- **Never use Authorization header** for ABS API calls — use `?token=`
- **Always use `credentials: 'omit'`** on fetch calls
- **Cache API URL fragments are stripped** — never use `#chunk=N` style cache keys, use query params
- **Cloudflare Pages `_headers` rules are additive** — don't use wildcards if you need a header to override; use explicit per-file rules
- **`Content-Range` is not CORS-safelisted** — use HEAD `Content-Length` for size discovery
- **iOS PWA memory cap (~50 MB)** — never `cache.put` a multi-hundred-MB Response or `arrayBuffer()` a huge cached entry; both crash the tab
- **iOS WebKit adds latency to SW-intercepted media fetches** — only intercept when something is actually cached
- **A media load must be all-SW or all-native** — iOS cancels when a response's CORS status differs from earlier ones; pin the mode per file at `MEDIA_LOAD`, bridge gaps with a Range-only CORS fetch, never mix
- **Never use cache-first** in the SW for JS/CSS files
- **Cache version must be bumped** when changing the on-disk format
- **Safari on macOS is the primary test browser** — strictest about CORS
- **ABS container name may change after updates** — always check with `docker ps`
- **`?purge` URL param** wipes all caches and unregisters the SW — escape hatch for stuck installs
- **ABS CORS origin caching** — avoid hitting ABS from multiple different origins simultaneously
- **`input type="url"`** rejects bare hostnames — use `type="text"` and auto-prepend `https://`
- **`reg.update()` is unreliable on iOS PWA** — pair it with a build-version probe (`fetch('/index.html?_v=…')` + parse `#build-version`) for reliable update detection
- **Don't trust "meta exists" as "fully cached"** — sliding-window writes meta upfront with chunks added incrementally; check actual chunk presence in validators

**Real-Debrid pacing** (`_abbAddPaced`, 2026-09-05). RD's torrents endpoints allow roughly one request a second per API key and one add spends several (addMagnet, info polls, selectFiles). Adding two at a time cost a 29-file release most of its files to `Real-Debrid 429: too_many_requests`, each row left with a manual Retry. Adds are now sequential with a 1.2 s gap, and a 429 counts down and retries itself (15 s, 30 s, 60 s, 60 s, 120 s) before the manual Retry button reappears. The shim retries a 429 four times over ~37 s underneath this. Don't restore parallel adds — the wall-clock saving was minutes and the cost was lost files. Same code in the shim's /admin (`abbAddPaced`).

**Which storage backend a book is on** (ABS_shim only). The shim adds a non-ABS `storage: {provider, name, detail}` to every entry in `media.audioFiles`; stock ABS sends nothing and both places degrade to hiding it. `_formatLabel` appends the name to the book page's "M4B · 64 kbps" line and `_renderFsFileInfo` adds a Storage row to the flip-side panel. It matters because the same title can exist on two backends as two separate library items with separate progress, and nothing else distinguishes them.

**Repeat grabs go back to the same folder (2026-09-06).** Before adding torrents, the grab asks `GET /api/admin/abb/grabs?hash=&title=&folderName=`. If this info hash was grabbed before, its recorded destination is reused and the row says "topping up" — that is what makes a second pass (to collect tracks the first one missed) complete the book rather than start a differently-incomplete second copy of it. Otherwise, if the library already holds something that looks like the same book, a confirm appears before anything downloads. `fetch-url/start` gets `sourceHash`/`sourceTitle` so the destination is recorded. Same code in /admin, including the On Real-Debrid resume path, which is where this went wrong.

**Delete from pCloud** (`App.isShim` only): long-press a book card (`_wireLongPress`, 550 ms; right-click on desktop) or tap "Delete from pCloud…" on the book page → `confirmDeleteItem` (shows format/length) → `DELETE /api/admin/items/:id?deleteFiles=1`. ## Background track boundaries (fixed 2026-09-06)

A multi-part book went silent at every part boundary while the app was
backgrounded (lock screen kept "playing", no sound, reopening restarted the
part from zero). Root cause and fix are in
`docs/background-playback-handover.md`; the rules that came out of it:

- **The pin must land before `src` is assigned.** `pinMediaMode` waits for
  the worker (8 s cap) — it used to time out at 500 ms, which the worker
  missed at every load, so every load began unpinned and attempt 1's
  "native" boundary was really a worker/native mix. The worker answers
  `MEDIA_LOAD` from its existing key map (`ensureKeys`); don't put
  `loadCachedKeys()` back there.
- **Pin the next part early.** `maybePrewarmNextTrack` pins the next file
  30 s before the boundary, so `onTrackEnded` assigns `src` immediately.
  This is the decisive change: a cold worker woken *at* the boundary, with
  the audio session already quiet, is what iOS would not carry through.
- **Native means native.** A freshly restarted worker (no key map) no longer
  answers online audio with `respondWith(fetch())`; it returns without
  responding and pins the file native (`forcedNative`) until the page's
  next `MEDIA_LOAD`. Offline keeps the old wait-for-cache path.
- **Both build hashes must match before a test counts.** `sw.js` carries
  `SW_BUILD` (stamped by `deploy.yml`), shown under the page hash in the tab
  bar and recorded in every crash log's `audio_state.sw`. A heartbeat
  (`hb`) is logged while hidden — 5 s, 1 s for the minute after a boundary.

## Cold launch paints before the network answers (2026-09-20)

A tail of the shim during a launch showed the server side finishing in about a second (`/api/libraries` 156 ms, `/personalized` 627 ms); the wait was the client's strictly serial sequence: login screen until `/api/libraries` answered, then a "Loading" spinner until `/personalized` did, with the in-memory tab cache forgotten on every relaunch. Now:

- **`tryAutoLogin` paints from the previous launch's library list** (`pholia_libraries:<server>|<user>` in localStorage, written by `_fetchLibraries()` on every path that loads libraries) and only then awaits `/api/libraries`. A changed list rebuilds the picker; a 401 with no silent re-login puts the login screen back; a network failure with cached shelves up just sets `_offlineMode` (the Downloaded row works, visibilitychange/online retry).
- **The home and Library tabs' last renders are persisted** (`pholia_tab:<build>|<server>|<user>|<tab>|<lib>`, see `PERSIST_TABS`/`_persistTab`/`_loadPersistedTab`; Library was added in ea5cdf9, the build hash in 79e52e3, so the first launch after any deploy takes the ordinary slow path and re-seeds). `_renderTab` paints it, binds, and runs the normal `_refreshTab` behind it; because card handlers are bound per element, an identical refresh must NOT re-bind (it doesn't — `prev !== out.html` gates the repaint). The persisted paint binds without its runtime data, so the two handlers that need it fall back on tap: offline cards look the item up in `Offline.listDownloaded()`, and `showSeriesDetail` fetches the series list when `_seriesCache` has no entry. Every `_tabCache = {}` reset goes through `_invalidateTabCache()`, which also drops the persisted copy; `logout()` clears it too. Keyed by server + user so another account's shelves can never paint.
- **The launch-time update checks are deferred 6 s** (`_updateChecksArmed`): `_checkBuildVersion` re-fetches index.html with no-store and `_pollForUpdate` re-downloads sw.js, and both were sharing the radio with the launch API calls.
- **Launch marks** go into the audio event ring buffer as `mark` events (`_launchMark`): `launch-html` (index.html downloaded, from the navigation timing entry), `launch-js`, `launch-shell`, `launch-home-cached`, `launch-libraries`, `launch-home` — ms since navigation start, first occurrence only. They ship with any crash log / manual Send, so before-and-after numbers come from D1 (`events_json LIKE '%launch-home%'`).

Verified on the phone the same day: shell 42 ms, cached shelves 56 ms, `/api/libraries` 457 ms, fresh shelves 3293 ms — and that last number exposed the next problem.

**The "fully downloaded" scan was the real cost, not the network.** The green dot on a card means every chunk of every track is in the offline audio cache, and deciding that meant re-reading and JSON-parsing every downloaded item's record plus listing every audio-cache key — on every tab paint (`markDownloadedCards` from `bindCardClicks`) and again in the home render, about a second each on an iPhone. That is why the dots lagged a tab switch and most of why fresh shelves took 3 s when the shim answered in 0.6. `Offline._fullyScan()` now memoises the answer on `_coverageVersion` (bumped by every page-side chunk write/delete, `saveMeta` and `notifySwCacheChanged`; the SW itself never writes audio chunks) with a 60 s TTL backstop, and `fullyDownloaded()`/`fullyDownloadedIds()` both read it. Two more launch marks, `launch-scan` and `launch-personalized`, split the home render's two halves so the next slow launch can be blamed correctly. The Library tab is persisted like home (`PERSIST_TABS`), so the first tap per launch no longer waits for the 200-item listing.

**The memo does not help a cold launch, so the home paint no longer waits for the scan (9344bd2, 2026-09-20).** The memo lives in page memory, so every launch still runs the scan once, and phone marks on 464e663 (2026-09-20 08:52 UTC: home-cached=1076, libraries=1363, scan=4523, personalized=4523, home=4526) showed the shelves data sitting there for 3.4–4.9 s waiting for it — `scan` and `personalized` at the same millisecond is the tell. Now `showHome`'s produce awaits only `/personalized`. The Downloaded row comes from `Offline.fullyDownloadedKnown()`: the last completed scan of this page load when its `_coverageVersion` still matches (a memo hit, free), a waited-for re-scan when a chunk was written or deleted since (that row is what you came back to look at after a download), and on a cold launch — no scan has completed yet — last session's list from localStorage `pholia_offline:<server>|<user>` (id/title/author, per server + user, NOT per build: downloads outlive an update). `_settleHomeOffline` runs from the bind step after every home paint, waits for the scan, saves the list, and if the row on screen shows a different set of ids swaps just that row — it lives in its own `.home-offline` box, always present, so the shelves keep their DOM, scroll positions and handlers — then rewrites `_tabCache[key].html` and the persisted copy from `bindData.shelves` so the next refresh still patches progress in place. Traps: the row's items in `bindData` are `null` on that cold path (the offline-card tap handlers already look the book up in the store, keep that fallback); `renderOfflineSection` must stay progress-bar-free or the settle's swap would change what `_PROGRESS_RE` counts; and a persisted-tab paint has no `bindData.shelves`, so a settle there patches the DOM only and leaves the cache html alone (the refresh behind it rebuilds both). Making the scan itself faster is still not an option — Cache Storage `keys()` over every chunk is what costs, and that is iOS. Verified on the phone the same day (manual Send, 10:09 UTC): html=317, js=436, shell=437, home-cached=449, libraries=676, personalized=694, home=695, scan=3723 — the fresh shelves land 19 ms after `/libraries`, and the 3 s scan arrives on its own behind them.

**A refresh that only moved progress bars patches them in place.** Card and grid markup embeds each book's progress as a bar width, and listening moves it, so nearly every background refresh produced HTML that differed from the last paint and `_refreshTab` swapped the whole tab's innerHTML a second or so after it painted (shelves jumped, a scrolled row snapped back, a tap could land on a card being replaced). Since 2026-09-20 the bar is always in the markup (`_progressBarHtml`, `hidden` at zero, so a book starting doesn't change the DOM's shape), `_progressNeutral` compares the two renders with widths and `hidden` blanked out, and when they match `_patchProgressInPlace` copies the widths onto the live bars and re-runs `markDownloadedCards` instead of repainting; bind is NOT called (per-element handlers would double-bind). Anything else — a book added, removed, reordered or retitled — still takes the full repaint. Keep the bar markup in the exact shape `_PROGRESS_RE` matches or every refresh silently falls back to repainting.

## Stuck seeks: a watchdog in loadTime (2026-10-14)

**The bug.** Crash log `907827f3` (iPhone, iOS 18.7, build d041e71): an mp3 episode fully buffered (`buf {n:1, sec:1884.6}`), network idle, readyState 4. Seeks with the same src fired `seeking` and never `seeked`, and `currentTime` stayed frozen at the target for minutes while the element said it was playing and sound carried on from somewhere else. The scrubber, ad skipping and progress sync all read `currentTime`, so the scrubber froze and an ad wasn't skipped. After a cold start the same file seeked in 34 ms. The root cause is unknown; the net below doesn't need it.

**What it checks.** `loadTime` arms `_armSeekWatch` for every same-src seek (`kind: 'seek'`), whatever the source (auto-rewind, buttons, ad skip, chapters, scrub, lock screen), and for every new load that starts part-way in (`kind: 'load'`, offset > 0), because WebKit seeks there once the metadata is in and that seek can stick too (below). A load at 0 has no seek and is not watched, and a recovery's own reload (`opts.recovery`) never is. A `seeked`, a later `loadstart` or a newer `loadTime` ends the watch, so a seek that finishes is never touched: traces of normal seeks and normal loads are identical to d041e71's. A seek's clock starts at once; a load's starts when the element plays (`_loadWatchTrigger`: `playing`, or `canplay` while not paused), which can be minutes later, and goes back to waiting if the element is paused again. At `SEEK_STUCK_MS` (2 s) `_checkSeekWatch` counts it as stuck only when all of these hold: same item and src, no element error, the target inside `audio.buffered` (a second of audio after it, or the range runs to the end of the file), `currentTime` still within 0.5 s of the target (a stuck clock sits exactly on it), and no recovery in the last `SEEK_RECOVER_COOLDOWN_MS` (30 s). While the element is still fetching (`networkState` LOADING) with less than `SEEK_LOADING_MARGIN_S` (30 s) buffered after the target, the seek may be waiting for those bytes: it is looked at again every 2 s and judged once the fetch is done. Fetching alone is no excuse: in 875e31d0 a request for later bytes stayed open 26 s while the target sat 1000 s inside the buffered range, stuck all along.

**The load case (crash log 875e31d0, 2026-10-14, the watchdog's first day on the phone).** A Continue Listening tap on an episode: `seek-call loadTime 0→430.72`, `play()` refused (see "A tap never waits on the downloads scan" below), `loadedmetadata` then `seeking t=430.72` at readyState 1 with nothing buffered, and no `seeked`, ever. 90 s later the user pressed play: `waiting`, `loadeddata`, `canplay`, `playing t=430.72`, and the heartbeats show the clock frozen at 430.72 for 30 s while playing. The UI showed the saved position and the audio played from somewhere else, very likely the start (the Peanut episode that morning played its 0:00 pre-roll while the UI said 1:25). That is "it starts from the beginning". The same log has the seek watchdog's first recovery: a chapter tap stuck, reloaded, `seeked` in 65 ms, played.

**Hidden pages are never acted on, but a stuck seek is not forgotten either.** A deadline that passes while hidden logs `seek-stuck act:'defer'` and leaves the watch armed. It is judged once the page is next visible (`_seekWatchVisible`, from visibilitychange), after `SEEK_VISIBLE_GRACE_MS` (1 s) so a seek the foregrounded decoder finishes by itself is left alone. This is for the lock-screen resume: its auto-rewind seek is issued while hidden, and iOS keeps a fully cached file's decoder asleep until the app is opened (`docs/background-playback-handover.md`). Nothing here runs in the background: that path is the fragile one, and changes to it were reverted three times in 2026-09.

**The recovery** (`_recoverStuckSeek`) re-runs the load at the target. It pins the worker first (`App.pinMediaMode`, while the element still holds the stuck load), and only then drops any pending silent-seek resume (`_silentGen`, so neither its `seeked` listener nor its 1500 ms fallback can act on the new load), calls `removeAttribute('src')` + `load()` and `loadTime(target, 'seek-recover', {pinned: true, keepPaused: !play, recovery: true})`, the ordinary src-change path, with nothing awaited between the clear and the new src. Clearing first and then waiting for the worker (up to 8 s) would leave the element at 0 meanwhile, and a sync or the local position save could record 0. It is abandoned if anything moved on during the pin wait (a newer seek, another item or src, the page hidden). It ships a crash log (`seek-stuck`) 5 s later, so whether it worked on the phone shows up in `crash_logs` without a manual Send.

**Keeping the user's intent.** It plays unless the seek was a `keepPaused` skip on a stopped player, or playback was paused since (for a load: since it started playing): by the user (`Player.pause()` bumps `_pauseSeq`) or by the system (the element's own `pause` event stamps `_pausedAt`), which matters because a deferred watch can be judged long after its seek. An element held paused by a pending silent seek counts as playing (`silentHeld` in loadTime): that is a second skip tapped quickly while playing, and its pending resume would have played it. A recovery that stays paused sets the play button to paused (a pause pressed during a silent seek fires no `pause` event) and keeps the pause for rewind-after-pause.

**Log lines** (ring buffer, `audio` tag): `seek-stuck {kind, source, to, off, t, buf, rdy, net, seeking, paused, ms, act, why}` with `act` recover / none / defer / wait and `why` cooldown / hidden / loading (plus moved-on, error, not-buffered or clock-moved, logged only to close a deferred or waiting watch); `seek-recover {kind, act: reload|abandoned, play, pin}`; and `page tap-item {from: known|scan|net|none, ms}` for where a tap's item came from. The reload's own `seek-call` reads `from: 0` because the element was just cleared.

**Known trade-off.** A seek into buffered audio that really takes longer than 2 s with the network idle looks exactly like a stuck one at the deadline, and gets reloaded at its target (one extra load, intent kept). Buffered seeks on the phone take tens of milliseconds, so this should not happen. Verified in a jsdom harness that drives the real player.js with a fake element that dispatches events (49 checks, including the exact 875e31d0 sequence and byte-identical traces against d041e71 for normal seeks and loads). The seek recovery was seen working on the phone in 875e31d0; the load recovery has not been yet.

## A tap never waits on the downloads scan (2026-10-14)

Crash log 875e31d0: on a cold launch the "fully downloaded" scan took 6.5 s (`launch-scan` 6527 ms), and a Continue Listening tap on an episode went through `playEpisode`, which awaited that scan before `Player.startItem`. Its `play()` came after the tap's user activation had lapsed: `play-rejected NotAllowedError`, the mini player up, nothing playing. "Sometimes it works" was a tap after the scan had finished. `quickPlay` (books) awaited the same scan, in parallel with the item fetch but still first.

Now both go through `App._itemForTap(oid, netP)`: the last completed scan's answer when it already holds the item (`Offline.fullyDownloadedKnown()`, free), otherwise whichever of the network item and the scan's answer arrives first with a usable item. A network item plays from the cache too, because the worker serves cached audio by URL. Only when the network fails (offline) is the scan waited for. The show page and episode page pass hints, so their taps need no fetch at all and now start at once. A show that no longer lists the episode is not a usable answer, so a downloaded copy still plays. A network failure with nothing downloaded still ends in the same "You're offline" alert. The queue's auto-next path (`opts.auto`) is unchanged. A Downloaded-row episode card on a persisted paint went through `listDownloaded()` (every downloaded record read and parsed) before `playEpisode`; its oid already says it is an episode, so it now goes straight there. `markDownloadedCards`, `_redrawEpisodeRow`, `syncKeptDownloads` and `_episodeFromPhone` still await the scan, but none of them sits between a tap and `play()`. Measured in a jsdom harness with a 3 s scan: tap to `startItem` went from 3062 ms to 54 ms on the network, and from 3007 ms to 4 ms with hints.
